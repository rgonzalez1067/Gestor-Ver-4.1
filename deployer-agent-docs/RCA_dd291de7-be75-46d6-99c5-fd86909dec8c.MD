# RCA — Full Backup download returns HTTP 410 ("archivo ya no está disponible")

**App:** admin-control-center-21 (tier_0 "Starter", template fastapi_react_mongo_shadcn, Cloudflare frontend)
**Active run:** dd291de7-be75-46d6-99c5-fd86909dec8c
**Verdict:** CONFIRMED root cause = the backup ZIP is written to a **single pod's local `/tmp`**, but the backend runs **2 replicas** with round-robin (non-sticky) load balancing. The download request is served by a *different* pod whose local `/tmp` never had the file → `os.path.exists(file_path)` is False → 410. It is **NOT** caused by an OOM, restart, or eviction.

---

## Answers to the four production questions

**1. Replica count / routing — THIS IS THE CAUSE**
- `replicas: 2`, `max_replicas: 2`, `hpa_enabled: false` (fixed at 2 pods).
- The two pods run on two different nodes:
  - `...-4w2gk` on node `...-knvr`
  - `...-skgt5` on node `...-dipi`
- Traffic reaches the backend through the standard Kubernetes Service (`/api/*` → backend). There is **no session affinity / sticky routing** configured — requests are distributed round-robin across the 2 pods. So a `build` request and a subsequent `export` request can (and here did) land on different pods.

**2. Is `/tmp` shared across replicas? — NO**
- `/tmp` is per-pod node-ephemeral storage. It is **not** a shared/network volume. Each replica has its own private `/tmp/full_backups/`. A file written by pod A is invisible to pod B, and is also lost on any pod restart/reschedule.

**3. Restart / OOMKilled / Eviction during the backup? — NO, none**
- Both pods: `restart_count: 0`, `state: running`, `ready: true`.
- No `OOMKilled`, no `Evicted`, no `last_termination` on either container.
- Only events present are transient `Startup probe failed: 503` during cold-start at 02:12 (normal boot warm-up), then healthy. Pods have been continuously up since `2026-08-26T02:11:51Z`.
- Timeline confirms the build pod stayed alive the whole time: backup doc `created_at` 02:13:56 → `ready_at` 02:19:18, well after the 02:11:51 start, with zero restarts. So the file was successfully written and persisted on that pod — it simply isn't on the *other* pod that served the download.

**4. Ephemeral storage headroom**
- Ephemeral storage limit is **1Gi (1024 MiB) per pod** (tier_0).
- The produced backup is **763,948,326 bytes ≈ 728 MiB** (from `backup_jobs`: `size_bytes: 763948326`, `status: ready`, 74/74 collections).
- 728 MiB fits inside 1Gi, leaving only ~295 MiB headroom. It did NOT trigger eviction this time (confirmed by #3), but this is a secondary risk: a slightly larger dump, or two concurrent builds on one pod, would exceed 1Gi and cause an ephemeral-storage eviction. Not the cause of the current 410, but worth removing alongside the fix.

`file_path` is a pod-local path with no pod identity — the download handler cannot know (or reach) the pod that wrote it.

## Why the 410 happens (mechanism)
1. `POST /admin/full-backup/build` runs a background thread on **pod A**, writes ZIP to pod A's `/tmp/full_backups/<job_id>.zip`, sets `backup_jobs.status=ready` + `file_path` in Mongo (shared).
2. User clicks download → `GET /admin/full-backup/export?ticket=...`. The Service round-robins this to **pod B**.
3. Pod B reads the same Mongo doc (status=ready, file_path set), but `os.path.exists(file_path)` is False on pod B's disk → handler returns 410.
4. It would succeed only on the (roughly 50%) chance the export lands back on pod A.

Mongo state is consistent across pods (shared Atlas); only the **file bytes** live on one pod's local disk. That mismatch is the whole bug.

## Fix (required — this is an application/source change, owned by E1; not a deploy/manifest fix)
Local pod disk cannot be used to hand a file between replicas. Move the artifact to shared storage:
- **Recommended:** write the ZIP to shared object storage (e.g. the platform's R2/S3 bucket, or GridFS in the same Mongo the app already uses) in the build thread; store the object key in `backup_jobs`. `export` streams from object storage, so any replica can serve it. This also removes the ephemeral-storage eviction risk for 700 MB+ dumps.
- **Interim / weaker alternatives (not recommended as the durable fix):**
  - Pin backend to `replicas: 1` — makes build & download share one pod, but loses redundancy, still loses the file on restart, and still risks the 1Gi ephemeral limit. Note: tier_0 is fixed at 2 replicas, so this needs a tier/config change.
  - Add Service session affinity (sticky) — fragile; breaks on pod restart and on the affinity window expiring; does not fix the 700 MB-on-1Gi risk.
- Regardless of transport, given ~728 MiB artifacts, stream the build output and the download rather than buffering in memory, and prefer object storage over `/tmp` so you are not bounded by the 1Gi ephemeral limit.

## What is NOT the cause (ruled out with evidence)
- Not OOM, not a crash, not an eviction, not ephemeral-storage exhaustion (restart_count 0, no termination, file reached `ready` and persisted on its pod).
- Not a Mongo/state issue (the `backup_jobs` doc is correct and readable from any pod).
